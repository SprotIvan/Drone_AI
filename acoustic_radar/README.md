# Acoustic Radar — акустичне виявлення дронів 🚁🎯

Система реального часу на **Raspberry Pi 5** + **ReSpeaker XVF3800 4-Mic Array**,
яка слухає ефір і піднімає тривогу, коли чує мультикоптер.

```
чути дрон            →  👀 Підозра  →  🆘 SOS ДРОН + напрямок + відстань
сторонні звуки/тиша  →  нічого не відбувається
```

---

## 📌 Що система робить

| Функція | Як реалізовано |
|---|---|
| **Класифікація** | Легка CNN (56 тис. параметрів) по Mel-спектрограмі, ONNX Runtime |
| **Рішення 2 рази/с** | Ковзне вікно 2 с із кроком 0.5 с |
| **Напрямок 360°** | Азимут із DSP масиву по USB, з фолбеком на власний SRP-PHAT |
| **Відстань** | Калібрований рівень у смузі 80–4000 Гц із відніманням фону |
| **Захист від хибних тривог** | Скінченний автомат: 2 підтвердження поспіль + гістерезис P_START 0.775 / P_HOLD 0.50 |
| **Тривога за 1.0 с** | 2 блоки × 0.5 с; утримання цілі 3.0 с при короткій втраті сигналу (`ALARM_COASTING`) |
| **Локальний веб-інтерфейс** | `main.py --web` — FastAPI + MJPEG на `0.0.0.0:5000`, транслює ТОЙ САМИЙ кадр, що й локальне вікно |
| **LED-кільце ReSpeaker** | Синє «шукаю» / червоний сектор на азимут цілі; команди беруться з переліку самої прошивки |
| **GUI** | Pygame-радар 360° з візуалізацією невизначеності |

## ⚠️ Це виправлена версія — стару модель треба перенавчити

`radar.py` відмовиться запускатись зі старим `acoustic_radar.onnx` і скаже про це
прямо. Це навмисно: стара модель була навчена на зіпсованих даних і з іншим
front-end, тому «працювала», але нічого не ловила.

Знайдені та виправлені причини поганої детекції описані нижче.

### 1. У класі «дрон» лежали НЕ дрони 🔴 головна причина

`download_dads.py` брав перші 30 `.wav` з архіву DroneAudioDataset:

```python
wav_files = [f for f in z.namelist() if f.lower().endswith('.wav')]
...
if count >= 30: break
```

Структура архіву:

```
Binary_Drone_Audio/unknown/     ← шум (ESC-50 + Speech Commands)
Binary_Drone_Audio/yes_drone/   ← власне дрони
```

У ZIP-архівах GitHub файли йдуть в алфавітному порядку, тому `unknown/` іде
**перед** `yes_drone/`. Усі 30 «записів дронів» насправді були фоновим шумом.
Модель училась відрізняти шум від шуму.

**Виправлено:** беруться файли виключно з `yes_drone/`, і всі (~1300), а не 30.

### 2. Навчання і Raspberry Pi рахували РІЗНІ спектрограми

`dataset.py` використовував `torchaudio`, а `radar.py` — власну NumPy-реалізацію.
Вони не збігались:

| | навчання (torchaudio) | інференс (старий radar.py) |
|---|---|---|
| Mel-фільтри | точна інтерполяція по частоті | округлення до цілих FFT-бінів |
| Вікно | `torch.hann_window` (періодичне) | `np.hanning` (симетричне) |
| Нижні Mel-канали | +4.6 дБ | **−25.5 дБ** на тому самому сигналі |

Косинусна подібність нижніх фільтрів падала до **0.73** — саме там, де живуть
гармоніки частоти проходження лопатей.

**Виправлено:** `features.py` — одна реалізація на NumPy для обох шляхів.

### 3. Модель залежала від гучності мікрофона

`mixer.py` нормалізував **кожен** семпл рівно до піку 0.95, живий мікрофон — ні.
Замір на старій моделі:

```
той самий сигнал, gain=1.00  →  P(дрон) = 0.047
                  gain=0.10  →  P(дрон) = 0.000
```

**Виправлено:** нормалізація спектрограми (mean/std) у `features.py`
+ рандомізація вихідного рівня в `mixer.py`. Тепер розкид P(дрон)
при зміні гучності у 100 разів — `0.0001`.

### 4. Датасет мав «ярлик»: low-pass = дрон

Симуляція відстані (Butterworth low-pass 7.5 → 2.5 кГц) застосовувалась **тільки
до класу 1**. Модель знайшла найпростіше правило «є завал ВЧ → дрон». Воно дає
чудову валідацію і нуль користі в полі, бо реальний фон теж має завал ВЧ.

**Виправлено:** ідентична симуляція відстані застосовується до обох класів.

### 5. Валідація була нечесною

`train.py` робив `random_split` **вже змікшованих** файлів, тому один і той самий
вихідний запис потрапляв і в train, і в val. «96% точності» означало
«модель запам'ятала 30 записів».

**Виправлено:** `mixer.py` розділяє **вихідні** файли на train/val до мікшування
і генерує дві незалежні папки.

### 6. У класі 0 не було моторів

Без записів двигунів, бензопил, гелікоптерів і пилососів модель не має шансу
відрізнити їх від дрона.

**Виправлено:** `raw_audio/hard_negative/` завантажується автоматично.
Заразом виправлено номери категорій ESC-50 — старий код підставляв
`17=wind, 22=chirping_birds, 24=insects`, а насправді це
`pouring_water, clapping, coughing`. **Вітер — найважливіший вуличний фон —
не потрапляв у датасет узагалі.** Тепер категорії обираються за назвою
з `meta/esc50.csv`.

### 7. Шумовий гейт глушив далеких дронів

`NOISE_GATE = 0.03` по **піку** відкидав ціле вікно ще до інференсу.

**Виправлено:** гейт по RMS у смузі дрона, на рівні цифрової тиші (−65 dBFS).
У тесті дрон детектується на рівні −52 dBFS — старий гейт його б не пропустив.

### 8. Тривога піднімалась через 10 секунд

Блокуюче читання 2-секундного чанка × 5 підтверджень = 10 с.

**Виправлено:** ковзне вікно з кроком 0.5 с.

### 8b. Навіть після цього тривога йшла 3.5 с, а не 2.5 с

EMA ймовірності стартувала з нуля: за `p_drone = 1.0` згладжене значення
давало 0.50 / 0.75 / 0.875 і перетинало поріг 0.775 лише на третьому
блоці — і тільки тоді починався відлік 5 підтверджень. Разом 7 блоків.

**Виправлено:** скориговано холодний старт EMA + 2 підтвердження замість
5 → **тривога за 1.0 с** (`radar.DetectorTuning`). Ціна: поріг 0.775
підібраний під 2% хибних тривог на одне вікно, тож двох вікон замість
п'яти достатньо рідше — якщо хибних тривог стане забагато, піднімайте
`detector_confirm_blocks`, а не поріг.

### 8c. Коротка втрата сигналу гасила ціль

Порив вітру, маневр або перепона на 1–2 блоки — і напрямок зникав з
екрана. **Виправлено:** явний стан `ALARM_COASTING` тримає тривогу й
останній достовірний азимут 3.0 с; UI підписує їх `LAST BRG` і `HOLD n/6`,
щоб не видавати збережене за виміряне.

## 🧭 Чому кут був неправильний

`get_usb_doa()` мав `except Exception: return 90`, тому **будь-яка** помилка
мовчки перетворювалась на 90°. А помилка була майже завжди:

```python
ast.literal_eval("0.273 3.688 2.993 2.993")   # → SyntaxError
```

`literal_eval` розуміє лише `[0.273, 3.688]` з дужками й комами, а `xvf_host`
зазвичай друкує значення через пробіл. Плюс:

* брався випадковий промінь `vals[-1]` замість домінантного;
* субпроцес (200–500 мс) запускався у головному аудіоциклі → переповнення буфера;
* один зашитий шлях до `xvf_host.py`;
* `SmartTracker` запам'ятовував перший кут і ігнорував усе далі 50° —
  тобто залипав на хибних 90° назавжди.

**Виправлено** у `doa.py`:

* парсинг регулярним виразом — формат не має значення;
* вибір найбільшої узгодженої групи променів;
* опитування у фоновому потоці;
* автопошук `xvf_host.py` + `XVF_HOST_PATH`;
* при збої — чесне `н/д`, а не фальшиве число;
* власний **SRP-PHAT** по сирих каналах як запасний варіант
  (похибка 0–10° на синтетичному тесті);
* виявлення «обробленого стерео», коли канали ідентичні й DOA рахувати нічим;
* `DOATracker` — циркулярне згладжування з перескоком на новий напрямок
  після 3 підтверджень.

## 📏 Чому відстань була неправильною

Був один рядок:

```python
dist_m = int(min(200, 6.0 / max(peak_volume, 1e-4)))
```

* константа `6.0` ніде не вимірювалась — метри були вигадані;
* `peak_volume` — пік за 2 с: один порив вітру задає «відстань»;
* фон не віднімався: у вітряну погоду виходило «36 м» при порожньому небі.

**Виправлено** у `ranging.py`: RMS у смузі 80–4000 Гц, віднімання фону
по потужності, калібрувальна точка «рівень на відомій відстані», згладжування
медіаною в лог-шкалі. Демонстрація стійкості з самотесту:

```
                новий метод          старий
без пориву:   ~60 м (32–112)        ~157 м
з поривом:    ~45 м (24–84)         ~9 м      ← стрибок на порожньому місці
```

Виводиться **інтервал**, а не одне число: акустична далекометрія одним масивом
реально дає ±40–60%. Без калібрування показується `н/д` — це навмисно.

## 🛠 Структура проєкту

```text
acoustic_radar/
├── features.py        # ⭐ ЄДИНИЙ front-end Mel-спектрограм (train == inference)
├── model.py           # CNN AudioCNN (56K параметрів)
│
├── download_dads.py   # Завантаження DroneAudioDataset + ESC-50
├── mixer.py           # Генерація датасету з симуляцією відстані
├── dataset.py         # PyTorch Dataset + SpecAugment
├── train.py           # Навчання, метрики, вибір порогу, експорт ONNX
│
├── radar.py           # ⭐ RadarEngine + консольний режим
├── radar_gui.py       # Pygame-інтерфейс (використовує той самий RadarEngine)
├── doa.py             # Напрямок: USB DSP + SRP-PHAT + згладжування
├── ranging.py         # Відстань: рівень у смузі, віднімання фону, калібрування
├── audio_io.py        # Вибір мікрофона і відкриття потоку
├── calibration.py     # Читання/запис radar_calibration.json
└── calibrate.py       # Інструмент калібрування + діагностика
```

У кожного модуля є самотест: `python features.py`, `python doa.py`,
`python ranging.py`, `python model.py`.

## 🚀 Запуск з нуля

### 1. ПК: дані, навчання

```bash
pip install -r requirements.txt

python download_dads.py     # дрони + фон + важкі негативи (~700 МБ трафіку)
python mixer.py             # 4000+800 семплів на клас, train/val роздільно
python train.py             # навчання → acoustic_radar.onnx + model_config.json
```

`train.py` наприкінці друкує матрицю плутанини і компроміс
«чутливість ↔ хибні тривоги», після чого сам обирає робочий поріг.

### 2. Raspberry Pi: встановлення

```bash
sudo apt-get update && sudo apt-get install libusb-1.0-0-dev libportaudio2 -y
pip install numpy onnxruntime sounddevice pyserial pygame-ce

# доступ до масиву без sudo
echo 'SUBSYSTEM=="usb", ATTR{idVendor}=="2886", MODE="0666"' \
  | sudo tee /etc/udev/rules.d/99-respeaker.rules
sudo udevadm control --reload-rules && sudo udevadm trigger
```

Скопіювати на Pi: `acoustic_radar.onnx`, `model_config.json`, `features.py`,
`model.py`, `radar.py`, `radar_gui.py`, `doa.py`, `ranging.py`, `audio_io.py`,
`calibration.py`, `calibrate.py`.

### 3. Raspberry Pi: калібрування (обов'язково для метрів і градусів)

```bash
python calibrate.py check      # діагностика: мікрофон, модель, DOA
python calibrate.py devices    # якщо треба вибрати інший мікрофон

python calibrate.py noise      # 20 с фону БЕЗ дрона
python calibrate.py range      # зависнути дроном на відомій відстані
python calibrate.py doa        # джерело звуку у відомому напрямку (2 точки)
```

Результат пишеться у `radar_calibration.json`. Дві точки в `range` дають ще й
реальний показник згасання замість припущення 22 дБ/декаду; дві точки в `doa`
виявляють дзеркальність напрямку обертання.

Якщо `xvf_host.py` лежить не там, де очікується:

```bash
export XVF_HOST_PATH=/шлях/до/python_control/xvf_host.py
```

### 4. Запуск

```bash
python radar.py              # консоль
python radar.py --debug      # + поріг, рівень фону, джерело кута
python radar.py --list-devices
python radar_gui.py          # графічний радар
python radar_gui.py --fullscreen
```

## 🎯 Як ще підвищити якість детекції

Код виправлено, але залишається обмеження **даних**: `DroneAudioDataset` — це
записи двох апаратів (Bebop, Mambo), зроблені **у приміщенні** з близької
відстані. Акустика вулиці інша.

Найбільший приріст дасть власний польовий запис **тим самим мікрофоном**:

```
raw_audio/drone/          20–30 хв вашого дрона на різних відстанях
raw_audio/ambient/        той самий майданчик без дрона
raw_audio/hard_negative/  авто, мотокоса, генератор, бензопила
```

Формат будь-який — `mixer.py` сам приведе до 16 кГц моно. Після цього
повторіть `python mixer.py && python train.py`.
